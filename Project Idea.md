# Zepto Data & AI Platform — Capstone Project Development Specification

## 1. Project Vision

Build **one connected AI/ML engineering platform** with three internally linked capabilities:

1. **Data Engineering Pipeline** — turns raw scraped catalog data into a clean relational store.
2. **Analytics & Machine Learning Pipeline** — profiles and models a customer-style dataset end to end.
3. **Generative AI Support Assistant** — answers Zepto policy questions using grounded retrieval over Zepto policy documents.

The three modules are independently assessable but must live in **one public GitHub repository**.

### Engineering Story

**GET DATA → UNDERSTAND DATA → BUILD INTELLIGENCE → SERVE IT**

# 3. Module 1 — Data Pipeline

## Objective

Create a raw-to-relational data pipeline:

**SCRAPE → CLEAN → CONVERT → STORE → QUERY → ANALYZE**

The source is intentionally a book catalog because the objective is to demonstrate reusable data-engineering mechanics.

## Data Source

Use:

**Books to Scrape — `books.toscrape.com`**

It is a public scraping-practice website requiring no login or paid API.

## Data Collection

Using:

- `requests`
- `BeautifulSoup`

Collect either:

- all books across at least **3 categories**, or
- the first **5 paginated All Products pages**

The final dataset must contain:

- **at least 60 books**
- **at least 3 categories**

For each book collect:

- `title`
- `price` as listed in GBP
- `star_rating` as text, e.g. `Three`
- `availability` as listed text
- `category`

## Data Cleaning

Create these cleaned fields:

| Source | Required cleaned field |
|---|---|
| Price | `price_gbp` as `float` |
| Star rating | `rating` as integer 1–5 |
| Availability | `in_stock` as boolean |
| GBP price | `price_inr` |

### Parsing Rules

- Strip the currency symbol from price.
- Convert GBP price to `float`.
- Convert `One`–`Five` to `1`–`5`.
- Parse availability into a boolean.
- If a field cannot be parsed:
  - use median imputation for numeric fields where appropriate, or
  - drop the affected row where appropriate.
- Document and justify the decision.
- The pipeline must not crash because of a messy row.

## Currency Conversion

Use the required project-defined fixed baseline:

**1 GBP = 105.50 INR**

This is an artificial assignment constant.

Do not depend on a live exchange-rate API for the required implementation.

The exact rate must be documented in the README.

Optional live currency lookup can exist only as an ungraded extension and must never replace the required fixed-rate path.

## SQLite Schema

Use a normalized SQLite schema with at least two related tables.

Example:

```sql
categories(
    category_id INTEGER PRIMARY KEY,
    category_name TEXT UNIQUE
)

books(
    book_id INTEGER PRIMARY KEY,
    title TEXT,
    price_gbp REAL,
    price_inr REAL,
    rating INTEGER,
    in_stock INTEGER,
    category_id INTEGER REFERENCES categories(category_id)
)
```

The exact names may differ, but the following are required:

- Primary key
- Foreign key
- Relationship between the two tables

## SQL Analysis

Write and execute at least **5 SQL queries** collectively demonstrating:

- `SELECT`
- `WHERE`
- `ORDER BY`
- `LIMIT`
- `DISTINCT`
- `IN` or `BETWEEN`
- At least one `JOIN`

Save both:

- Query text
- Query output

## Pandas Reproduction

At least two SQL query results should be read using:

```python
pd.read_sql(...)
```

The JOIN query must also be reproduced using:

```python
pd.merge(...)
```

Show that the SQL and Pandas approaches produce equivalent output.

## Part A — Profiling and Cleaning

### Dataset Profile

Report:

```python

df.describe()
df.shape
```

For every column with missing values, report its missing percentage.

## Missing-Value Rule

Apply the threshold rule per column:

- **<5% missing:** drop affected rows
- **5%–30% missing:** impute
- If missingness is so high that imputation is unreliable:
  - drop the column, or
  - encode missing as its own category
  - justify the decision

Record the exact missing percentage before deciding.

- Categorical encoding for:

Transform Train

Never fit preprocessing on:

- Test data
- Full dataset before splitting

# 15. LangGraph Workflow

Create a LangGraph `StateGraph`.

Use a `TypedDict` state.

The graph must contain at least these three nodes:

```text
classify_intent
       │
       ├───────────────┐
       ▼               ▼
policy_question   general_question
       │               │
       ▼               ▼
retrieve_and_answer  direct_answer
```

## Node 1 — `classify_intent`

Classify each query as:

- `policy_question`
- `general_question`

### Required Mock Logic

When `MOCK_LLM` is unset or `1`, use the required keyword heuristic.

A query is a `policy_question` when its lowercased text contains one of:

```text
delivery
return
refund
membership
tracking
cancel
gift card
support hours
```

Otherwise:

```text
general_question
```

No LLM call should occur in mock mode.

### Optional Real-LLM Mode

When:

```text
MOCK_LLM=0
```

the optional real LLM may perform classification.

---

# 16. `retrieve_and_answer` Node

For `policy_question`:

1. Embed the query.
2. Retrieve the **top 3** most similar ChromaDB chunks.
3. Use cosine similarity.
4. Return an answer grounded in retrieved context.

Retrieval itself always runs in both mock and real modes.

### Mock Mode

Return a deterministic response based on the top retrieved chunk:

```text
Based on the retrieved context: <top chunk snippet>
```

A short excerpt, such as approximately the first 200 characters, is sufficient.

No LLM call occurs.

### Real-LLM Mode

Use the structured prompt and retrieved chunks to generate a grounded answer.

---

# 17. `direct_answer` Node

For `general_question`:

### Mock Mode

Return a fixed deterministic response, such as:

```text
I can only answer questions about Zepto policies right now.
```

No retrieval and no LLM call are required.

### Real-LLM Mode

The optional real LLM may answer directly without retrieval.

---

# 27. Core Design Principles

The project should be developed around these principles:

### 1. Reproducibility
A fresh environment should be able to reproduce the major outputs from documented commands.

### 2. No Data Leakage
Especially in Module 2, preprocessing and SMOTE must never leak information from the test set into training.

### 3. Deterministic Baseline
Module 3 must work without relying on an external LLM service.

### 4. Clear Separation of Concerns
Scraping, cleaning, storage, modeling, retrieval, orchestration, API, and containerization should have understandable responsibilities.

### 5. Evidence-Based Interpretation
Charts and model metrics should always be accompanied by written interpretation.

### 6. End-to-End Usability
The final project should not merely contain isolated notebooks. Each module should have a clear execution path.

### 7. One Coherent Platform
Although the three modules use different datasets and technologies, they should read as one AI/ML engineering capability:

**Data → Analytics → Intelligence → Service**
